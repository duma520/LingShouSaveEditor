# LingShouSaveEditor - 软件升级迭代记录

> 灵兽江湖存档修改器 · Python 3.10 + PySide6 (Qt6)
> 当前版本：**v2.14.3**（2026-09-16）
> 主程序：`LingShouSaveEditor.py`（唯一编译源，最终更新版）
> 作用：读取/粘贴 灵兽江湖 `*.es3` 存档，枚举并修改 **"ItemHad"** 段道具名称与数量，一键 9999、单个编辑、新增/删除/**一键添加全部**道具、**一键 _GetTimeNew→0**，其余数据段逐字节保留；**主角/队友「功法」增删(v2.14.0)**——内功 InKangFuHad / 武功 KangFuHad / 绝技 KangFuSkillHad / 轻功 KangFuQingHad 四段(队友段名加下划线前缀)，主角页与每个队友页均可多选/批量添加或删除(章节按功法在 `dataset/kangfu` 下的分支自动判定，不会放错；**已装备的功法不会被重复添加(v2.14.1)**，避免同名两份导致游戏里卸不下来)；每次读档自动把 ItemHad 道具名去重收录到 **道具名.json** 道具名库，并可**一键整理道具名**把当前存档(表格)已有道具名即时补入 json；**「打开上次」+「最近 ▾」历史（历史记录.json）**一键重开上次/历史文件，**「重新读取」**在游戏再次存档后重读当前文件；点表头可按**名称/数量排序**（不影响修改，支持升/降双向：点击=升序、同列再点=降序、右键可直接选方向）；**新增道具**可选/搜（中文·拼音全拼·首字母·数字）、多选/全选一次添加多个，并可勾选**仅显示缺少**与个人背包对比后一键补齐；**批量目标值持久保存**（设置.json）——「全部改为」目标值改后自动记住、重开仍保留，左侧按钮同步显示；**多角色分页(v2.0.0)**——主区按「道具 | 主角 | 每个队友」分页签，可对主角与**全部队友**逐字段改等级/经验/属性/血量/特性点/已用点等（带一键默认），整组改 武学经验(KongFuTypeLv) / 生活技能(LifeExp) / 六维(SixProCurrent) / 好感度(FriendLoveNum)，并可新增/删除地图标注点(_ActiveMap)；**队友按 _AbName 自动枚举(v2.1.0)**——不论在队(AddFriends)、离队(LeaveFriends)还是以后游戏新增的容器/队友都会自动出现可改页签；**大档后台线程打开(v2.2.0)**——超过约 600KB 的存档解析/角色模型改在子线程完成，打开/重新读取窗口不卡死，另把角色页改为**数据驱动建模**（`char_model` 单遍收集）大幅降低建页耗时。**道具搜索过滤(v2.3.0)**——道具页表格上方新增搜索框（与「新增道具」一致的中文/拼音全拼/首字母/数字 + 匹配方式切换），输入即实时过滤当前表格，便于快速定位要删除/修改的道具（# 列仍显示完整列表原序号）；双击编辑、删除选中只作用于过滤后的可见行，清空搜索框即恢复全部；新增/一键添加道具后自动清过滤以显示新行。**地图标注点搜索防重(v2.3.1)**——地图标注点(_ActiveMap)输入框输入时实时过滤下方已有地点便于查重，添加与已有相同的地点会被拦截并提示，不会重复。**地图跳转点库/批量添加(v2.4.0)**——`_scaffold/build_map_jump_points.py` 从 MapJumpTable.bytes(ES3 二进制, List<MapJumpTableItem>)提取每条记录 name(跳转点显示名, 含无 id 记录)去重排序生成程序目录 `地图跳转点.json`(236 个, 真实档 _ActiveMap 29 全覆盖); 地图标注点区新增「从地图跳转点批量添加…」——搜索(中文/拼音)/多选/全选一次添加多个, 默认只列未标注的, 与已有重复自动跳过。**新增道具按分类浏览(v2.6.0)**——「新增道具」弹窗改左右双栏：左栏分类树(勾选)按 内存所有道具.json 的 dataset 路径分级(大分类→小分类→细分类)，覆盖 equip装备/item道具/recipe配方/bookcontent书籍/kangfu武功秘籍/skillcom技能合成/shanhailu山海录 7 大类；勾选某分类即把该分类及全部下级道具纳入右侧候选(可多选大/小/细分类、勾「大分类」自动含所有下级、展开反选子分类可精确排除[父自动半选])；右栏保留搜索/多选/全选/自定义名/「仅显示缺少」，分类+搜索可叠加。数据源 程序目录 `道具分类.json`(由 `_scaffold/build_item_categories.py` 生成)，缺失自动回退 道具名.json 平铺。**剧情变量「善恶值」编辑（v2.12.0）**——主角页新增「剧情变量(存档 saveDialogue 段)」分组：游戏把「善恶值」这类剧情累计值写在 saveDialogue 段的变量表里，其形态不是 `"善恶值" : 7` 而是**十进制字节数组**编码（字符串 `83,<长度>,<UTF-8 字节...>` / double `78,<8 字节小端 IEEE754>` / bool `66,<1 字节>` / int32 `84,<4 字节小端>`）；实测 custom0.es3 为 `83,9,229,150,132,230,129,182,229,128,188,78,0,0,0,0,0,0,28,64` 即 **善恶值 = 7.0**（全档仅 1 处），因此新增纯函数 `dec_byte_text`/`dialogue_var_span`/`get_dialogue_var`/`set_dialogue_var` 做字节层读写（只换那 8 个字节、其余逐字节保留；变量不存在不凭空插入），主角页可直接读/改并带「默认 0」按钮，与角色属性一样随「保存/另存为/复制结果」落盘。

## 五、核心解析/生成逻辑（升级与扩展必读）

### 5.1 es3 存档里 ItemHad 的规律
```
		"ItemHad" : {"铜钱":{                    ← 段头 + 第一件物品头(内联)
				"_DressType" : 1,
				"_Count" : 998720404,            ← 数量
				"_Name" : "铜钱",                ← 与字典键同名
				"_LockHp" : 0,
				"_GetTimeNew" : 10101121200.116  ← 末字段无逗号
			},"2纯铜矿":{                        ← 上一件闭合 '}' + 下一件头 ',"名":{'
				"_DressType" : 1,
				"_Count" : 9999,
				"_Name" : "2纯铜矿",
				"_LockHp" : 0,
				"_GetTimeNew" : 0
			}
		},                                       ← 最后一件闭合 '}' + 段尾 '},'
```
- 每个道具固定 5 个字段，顺序为 `_DressType → _Count → _Name → _LockHp → _GetTimeNew`。
- 绝大多数道具 `_DressType=1 / _LockHp=0`，但**个别道具存在非默认值**（参考存档里 7 处 `_LockHp=100`、某些 `_DressType=2`）——本工具一律**保留原值**，仅新增道具用默认值（1 / 0 / 0）。
- 缩进：段头 2 个制表符、字段 4 个、物品闭合 `}` 3 个、段尾 `},` 2 个（**解析时按实际捕获，不硬编码**）。
- **每次游戏保存，ItemHad 的道具数量会增删变化**（这正是本工具要处理的核心）。

### 5.2 设计原则：只重建 ItemHad 段，不动其它
- es3 是 Unity EasySave 风格的文本序列化，**不是标准 JSON**，全文件通用解析成本高且易错。
- 本工具采取「**行级解析 + 整段重建**」：`parse_itemhad` 只解析 ItemHad 段 → 用户改物品列表 → `apply_itemhad_text` 把新段拼回 `lines[:start_idx] + 新段 + lines[close_idx+1:]`，**其它段落逐字节保留**。
- 因此改动永远只影响 ItemHad 段；段落之外的任何内容（包括空行、换行风格、缩进）原样保留。

### 5.3 兼容性细节（历史踩坑，勿回归）
1. **CRLF / LF 都要支持**：存档通常是 `\r\n`。凡以 `$` 结尾的行匹配（`^\s*\}$`、`^\s*\},$`）必须对 `ln.rstrip("\r\n")` 后的字符串匹配，否则 CRLF 下永远找不到段尾（曾导致解析扫到整个文件尾部、道具数虚高）。
2. **段头 `{` 的归属**：`find_itemhad_line` 的正则 `"ItemHad"\s*:\s*\{` 会把开头的 `{` 一起吞进匹配，故首件物品名应从 `suffix`（以 `"名":{` 开头）直接匹配 `"([^"{}]+)":\{`，不要再补前导 `\{`。
3. **勿误中 `ItemHadTemp`**：定位用完整键名 `"ItemHad"`（带引号），可避免命中 `"ItemHadTemp"` 等前缀相似段。
4. **BOM**：读写自动剥离/补回 UTF-8 BOM（`read_es3_text`/`write_es3_text`）。
5. **名称合法性**：道具名不能含 `{ } " \` 与换行（否则破坏格式）；新增/改名时用 `validate_item_name` 校验 + 查重。
6. **`_DressType` / `_LockHp` / `_GetTimeNew` 保留原值**：解析时以文本形式记录（`dress_type`/`lock_hp`/`get_time`，默认 None），重建时非 None 原样输出、None 才用默认值（1 / 0 / 0）。**历史教训**：曾把 `_LockHp` 硬编码为 0，导致参考存档往返不一致（该档有 7 处 `_LockHp=100`）；必须保留原值，否则会破坏存档。

### 5.4 扩展建议（后续功能入口）
- **新增设置项 / 历史**：最近打开历史（v1.3.0）存程序目录 `历史记录.json`（`load_history`/`save_history`/`push_history`），最新在前、大小写去重、上限 10 条，GUI 层在 `_record_history`/`_remove_history`/`_clear_history` 调用。若需持久化用户设置，建议沿用程序目录 JSON 式（与历史/道具名库同风格），键读写成对实现。
- **新增对 ItemHad 之外段的编辑**：以 `find_itemhad_line` 为模板，写对应段的定位/解析/重建函数（如 `find_xxx_line` + `parse_xxx` + `build_xxx`），再接入 GUI 新 Tab。

### 5.5 道具名库(道具名.json)逻辑
- **来源**：`extract_item_names` 只取 **ItemHad 段**（复用 `parse_itemhad` 的字典键），**不**扫全文件 `_Name`。
- **收录时机**：`_load_text`（打开/粘贴成功）后自动调 `merge_item_names_from_text` → 提取 + 与库合并去重 → 有新增才原子写盘（tmp+os.replace）。
- **存储**：程序目录 `道具名.json`（JSON 字符串数组，排序、去重、`ensure_ascii=False`）。打包 exe 后放 exe 目录（`app_dir()` 处理 frozen 分支）。
- **一键添加**：`_on_add_all_items` 读库 → 过滤当前已有 → 追加（数量 9999）→ 刷新表格。
- **注意**：早期曾全文件提取 `_Name` 得 1692 名，混入 perk(如 `铸甲匠1perk`)/好友名(兔千千/阿守)/技能效果名；改为**仅 ItemHad 段**后 757 名纯净无噪音。

### 5.6 拼音表(拼音表.json)逻辑
- **用途**：仅“新增道具”对话框搜索（中文/拼音全拼/拼音首字母/数字），运行时不依赖 pypinyin。
- **生成**：`_scaffold/build_pinyin_map.py` 用 pypinyin 从 `道具名.json` 提取汉字生成 `{汉字: [拼音]}`，当前覆盖 **1014 汉字**（约 14KB）。道具名库收录到**新汉字**后重跑即可。
- **读取**：`load_pinyin_map` 返回 dict（str 值自动包成 list），缺失/损坏返回 `{}` → 搜索退化为仅中文/数字（功能不中断）。
- **匹配**：`filter_item_names(names, query, pmap, mode)`，mode=0 自动 / 1 仅中文 / 2 仅拼音；`_name_pinyin` 数字/字母原样保留，未收录汉字退回其本身。

10. **装备页当前件要跟着「点的那一行」（v2.13.2 修复）**：`_on_equip_name_selected` 必须用 `spans[cur[1]][0]`（左侧点第几件就取第几件）设 `_equip_inst_open`，**不要写回 `spans[0][0]`**——否则点重名装备的第 2 件时，右侧技能表/属性其实还是第 1 件的（旧 bug）。
11. **技能库白名单（v2.13.3，务必延续）**：技能名.json / 技能候选只来自 内存所有道具.json 的 dataset/skill 里 **pass（被动/战斗）与 todu（特殊/临时）** 两组——生活技能天赋 `lifeperkskilltesk`、工具 `tool`、测试/未整理 `totest` 一律不出现。改生成脚本或重生成数据时**必须保留白名单**（`build_skill_names.py` 的 `KEEP_SUBS`），且**主程序 `load_skill_categories()` 的过滤不能删**（它挡的是旧 json/重生成混入，新增用例已覆盖）。排除只作用于**候选列表**：存档里已存在的技能（哪怕是这些类）读取/修改/删除不受影响。数量文案一律用 `skill_lib_count()` 动态取，不要写死数字。
12. **功法四段规律与写法（v2.14.0，务必延续）**：主角已学功法分四段，段名由功法在数据集里的分支决定——`dataset/kangfu/inkangfu/*`→`InKangFuHad`、`dataset/kangfu/kangfu/*`→`KangFuHad`、`dataset/kangfu/uniqueskill/jue/*`→`KangFuSkillHad`、`dataset/kangfu/uniqueskill/qing/*`→`KangFuQingHad`；**队友的段名前面多一个下划线**。新增/删除一律走 `kangfu_add`/`kangfu_del`（内部自行重定位容器内段与条目，**不要用调用方缓存的旧偏移**；不要自己拼 `text[:s]+v+text[e:]`，要走 `_apply_subs` 维护结构索引缓存）。新增条目字段必须按段类型用 `_kangfu_fields_text` 的模板（内功 8 字段/武功 6 字段/绝技与轻功 3 字段）；空段的首条目内联在 `{` 之后；删除时末条目要带上前面的逗号、非末条目带上后面的逗号，整段删空要回到 `{\n<段缩进>}` 的空字典形态（与游戏原生空段逐字节一致）。功法名比较一律用 `_kangfu_norm`（去空白与零宽字符），因为游戏数据里有 `2见微知著\u200c` 这类带零宽字符的名字。
13. **已装备的功法不能重复添加（v2.14.1，务必延续）**：添加功法前必须先读该角色「已装备」的功法 —— `kangfu_dressed(text, container_open)` 扫角色容器**直接**的 `Dress*KangFu*` 字段（`DressInKangFuName` 内功名 + `DressInKangFu` 对象里的 `_DressKangFu[]` 已装备武功 / `_DressQuickKangFu{}` 快捷武功 / `_DressKangFuQing` 轻功；队友这些字段带下划线前缀），**已装备的一律跳过**。原因：这些名字**不在** `*Had` 段里（实测 5 名角色的 19 个装备名 0 个在段中），往段里再添一份同名 = 同名的两份 → 进游戏这门功法**卸不下来 / 切不走**（用户实测反馈）。`kangfu_add` 的 `dressed` 参数不要删（传 None 会自动读）；GUI 里 `existing` 要并入已装备名（灰显 + `AddItemDialog.existing_tips` 说明），状态栏要分开提示「已学过」「已装备」。改完务必跑 `_scaffold/e2e_kangfu.py`（它会逐人逐名试写所有队友的装备名，验证都写不进去）。
14. **测试不要依赖「库里还有没学过的功法」（v2.14.2，务必延续）**：本工具的用户会把角色学到接近全库（实测主角 998/1045 门、队友藏玲珑 1003 门），所以真实档用例里「挑一门未学过的功法来添加」会**选不出名字**（报 `TypeError: 'NoneType' object is not subscriptable` / `IndexError`）。正确做法：① 逐个角色/逐段找候选并**容错**（找不到就 print 跳过）；② 更稳的是用「删一门已有功法 → 按库归属加回 → 再删掉」的通用往返（e2e_kangfu.py 已如此）；③ 挑候选时还要排除「已装备」的名字（`kangfu_dressed`）。另外「队友添加是否影响主角」要用 `kangfu_brief` 快照比较，不能断言「该名字不在主角列表里」（主角可能也学过同名）。
15. **等级框即时保存（v2.14.3，务必延续）**：「添加功法…」的等级 `_Lv` 走「输入框 `valueChanged` → `KangFuDialog._lv_changed` → 主窗 `_remember_kangfu_lv` → **立即 `_save_settings_now()`**」——不要退回「等点确定后 `_autosave_settings()` 防抖」的写法（用户明确要求输入完就保存，且点「取消」也算记住）。注意：`KangFuDialog` 构造里 `count_spin.setValue(default_lv)` 必须发生在 `connect` **之前**（否则会误触发一次写盘）；`_remember_kangfu_lv` 要 clamp 到 `0..MAX_ITEM_COUNT` 并返回夹紧后的值（调用方拿它当写入等级）。新设置项照旧要在 `_save_settings_now` 里成对写入。
16. **大批量列表/表格操作的三条铁律（v2.14.4，务必延续）**：
   ① **候选列表严禁逐行 `setSelected(True)` 做「全选」**——每行都会触发 `itemSelectionChanged` → 统计刷新（大库上 4565 行 = **26 秒**）。一律用 `_select_enabled_items(lst)`（连续可选行合并成区间 + `QItemSelection` 一次性提交，实测 50ms）；批量清空/填充列表要包在 `_BulkListEdit()`（暂停重绘 + 屏蔽信号，末尾手动刷一次 `_update_stat()`）。新增任何「大列表对话框」都要照此办理，并保留「灰显(不可用)项不被全选选中」的语义（`ItemIsEnabled` 判断）。
   ② **往道具表格加行不要 `_reload_table()` 整表重建**（4000 行 ~1.1s），用 `_append_rows_local(start)` 只建新增行；只有在**有搜索过滤**（`self._filter_map is not None`）或搜索框非空时才清搜索 + 整表重建（过滤下行号≠数据序，必须重建）。
   ③ **纯函数里批量写条目不要「每条重扫容器再整段拼接」**（O(k²)，段越大越慢）——先收集所有条目文本、`",".join` 成一块，再一次性插到锚点（`kangfu_add` 已如此）；能放后台的重算（列表/已装备信息等纯计算）就放进 `_run_bg` 的 worker，主线程只做控件填充。
   改完这三块务必跑 `_scaffold/bench_bulk_add.py` 复测（警戒线：全选 4565 行 < 0.5s、加 500 行 < 0.5s、功加 300 门 < 1s）与 GUI 冒烟里的 6 条性能回归守卫。
17. **多线程 / UI 响应性：每次更新都必须评估（v2.14.5 起强制）**：任何新增或改动的功能，先自问「这段会不会 >100ms / 在主线程还是后台」——**纯计算与文件 IO 一律 `_run_bg` 后台**（worker 里绝不碰 Qt 控件）；**Qt 控件只能在主线程建，所以长构建要分块 + `_pump(进度文案)` + 重入守卫**；列表/表格批量操作必须批量化（`addItems`/`_append_rows_local`/`_select_enabled_items`）。底层扫描两条铁律：`_matching_end`/`_entry_values` 走**配对表 O(1)**（勿退回逐 token 扫描）、字段名全档唯一时读取用 `_unique_field_open` + `_local_span_end`（勿用 `_locate_container` 扫大容器、也勿用 `_matching_end` 触发索引冷建）；改过 `self._text` 必须调 `_mark_dirty()`（内部会后台预热索引）。**完整清单、实测基准表与警戒线见「八、多线程与 UI 响应性约定」——提交前逐条过一遍，并用 `_scaffold/bench_ui_ops.py` 复测。**
18. **功法黑名单：数据文件与两条拦截都要保留（v2.15.0，务必延续）**：黑名单存**程序目录 `功法黑名单.json`**（程序级、与存档无关，`get_kangfu_blacklist_path()`；兼容 `{"items":[...]}` 与手写 `["名",...]`，`save_kangfu_blacklist` 原子写）。**两道拦截缺一不可**：① `KangFuDialog(..., hidden_names=self._kangfu_blocked_names())` —— 候选里**完全不显示**（靠 `AddItemDialog.hidden_names` + `filter_cat_data` 剔分类库，注意 **`filter_cat_data` 返回新对象，绝不要就地改 `_CAT_CACHE` 里的分类库**）；② `_on_kangfu_add` 确定后 `names = [n for n in raw if _kangfu_norm(n) not in bl]` —— 拦下**手动输入/自定义名**（它们不走候选列表）。名字比较一律用 `_kangfu_norm`（游戏里有带零宽字符的名字，黑名单里存脏名也要能命中干净名）。新增任何「黑名单/隐藏名单」类功能时：都放到 `self._kangfu_blacklist` 同款模式（启动加载 → 对话框即时写盘 → 关闭后重载并刷新界面标注），并同步更新 `_HELP_TEXT`。
    **v2.16.0 补充**：两个名单（功法/道具）共用 `_load_blacklist_file`/`_save_blacklist_file`/`_blacklist_keys` 与对话框基类 `BlacklistDialog` —— 新增第三个名单时**只需写一个子类**（类属性 + 4 个方法 + 可选的 `_make_extra_buttons`），不要再拷一份对话框代码。拦截必须有**两道**（`hidden_names` 让候选不显示 + 确定后再按归一化名过滤一遍，因为手动输入/自定义名不走候选列表）；「一键清除」类功能一律：**纯函数做文本改写**（如 `kangfu_purge_blacklisted`，按容器开括号**降序**处理、带偏移健全检查）+ **worker 里跑** + **确认框汇总要删的条目** + 只在确认后才 `self._text = nt`（取消则存档保持原样）

## 八、多线程与 UI 响应性约定（★ 强制，每次更新必须遵守）

> 本章是 v2.14.5「多线程全面优化」的固化结论。**今后任何新增/修改功能，都要先回答两个问题**：
> ①这段计算会不会 >100ms？②它在主线程还是后台？只要 >100ms 又不属于「Qt 控件操作」，就必须搬后台或分块。

### 8.1 三条硬规矩

1. **纯计算 / 文件 IO 一律后台**：任何预计 >100ms 的解析、扫描、排序、json 读写、写盘，都必须走 `_run_bg(work, msg)`
   （或大档打开走 `_open_big` 那套）。worker 里**只做纯函数与 IO**，绝不碰任何 Qt 控件（Qt 不是线程安全的）。
   已经这么做的：大档打开/粘贴/保存/另存/复制、商店记录/装备模型/蛊虫模型、添加/删除道具·功法·蛊虫·装备·卖品、
   批量参数、道具名库整理、结构索引预热。
2. **Qt 控件只能在主线程建，所以长构建要「分块 + 进度泵」**：用 `self._pump("正在构建角色页 5/23…")` —— 它会更新状态栏
   并 `processEvents()` 一次，**期间会临时禁用中央区与工具栏**（防用户在 processEvents 里重入）。
   配套必须有重入守卫（如 `_reload_table` 的 `_table_reloading`）。已分块：道具表重建（每 400 行，仅打开流程传 `progress=`）、
   角色页构建（每 2 页）、打开流程的各阶段。
3. **批量列表/表格操作必须批量化**（详见「维护要点 16」）：候选列表「全选」用 `_select_enabled_items`（区间 + `QItemSelection` 一次性提交），
   批量建项用 `addItems` 而不是循环 `addItem(QListWidgetItem(...))`，往表格加行用 `_append_rows_local` 而不是整表重建。

### 8.2 底层扫描：配对表与 fast 定位（勿退回旧写法）

- **`_struct_index` 现在返回 `(poss, chars, pairs)`**，`pairs` 是同型括号配对表（建索引时栈一次算出）。
  `_matching_end` 是 **O(1) 查表**（0.3ms），`_entry_values` 整块跳子容器、只遍历顶层字段（大容器 200ms → 18ms）。
  **不要**把 `_matching_end`/`_entry_values` 改回「从起点逐 token 扫到闭括号」；`_apply_subs` 的索引打补丁**会同步重建 `pairs`**。
- 配对表缺失/异常时会自动退回原逐 token / 全括号计数实现（语义与老版本一致）—— 这是保底，不是常态。
- **字段名在全档唯一时，读取不要用 `_locate_container(scope)`**（要逐层扫大容器，实测 `SCOPE_MAP` 1.7s）：
  用 `_unique_field_open(text, field, "["/"{")`（str.find，毫秒级）+ **`_local_span_end` 局部配平**（不要用 `_matching_end`，
  它虽已是 O(1)，但首次会因索引冷建而卡 1.3s）。已应用：`get_str_array`/`add_str_array`/`remove_str_array`（`_ActiveMap`）。
  同理 **`saveFriendData` 段名也是全档唯一的**：队友相关定位一律走 `friend_value_open`（`str.find`），
  **不要**回到 `_locate_container(["saveFriendData", "value"])`（第一层的按行正则要扫 28 万行 ≈ 70ms/次）。
- **单个大对象上不要用 `_entry_values` 反复枚举**（v2.17.0）：它每条都要切片 + 跑 `_key_value_offset` 正则，
  在 150KB/56 字段的队友对象上要 **~33ms/次**（`friend_blocks` 每人两次 → 20 人 1.6s）；
  改走 **`_direct_entries(text, open_i)` 快路径**（配对表跳子容器 + `str.find` + `_string_end`，全 C 级）后降到 **~3ms/次**。
  选型口径：**小段（几 KB，如功法段/商店段）用 `_entry_values`/`_kangfu_entries` 没问题；大对象（几十~几百 KB 以上）用 `_direct_entries`**；
  两者返回的键/区间语义一致，配对表缺失时会返回 `None`，调用方回退 `_entry_values`（保底）。
- **`_apply_subs` 的代价与「替换文本长度」成正比**（v2.17.0 实测）：它的索引打补丁要对替换文本逐引号重扫结构字符 ——
  替换 1 字节 **162ms**（纯 10MB 重拼的底），替换 2.4MB **1.64s**。所以**改写段落时要做「最小跨度」**，
  例：`friends_move` 不做「重建整个容器体」，而是「最后一个保留条目之后的尾区一次替换 + 尾区之前的连续被删段各一个最小跨度」
  （单人搬移 2.9s → 0.6s）。**新增写路径请先估算替换文本长度**：超过百 KB 就想办法拆小 / 只改差异区。
- **编辑后要预热索引**：写路径统一走 `_mark_dirty()`，它内部 `_preheat_index_async(self._text)` 在后台把新文本的整档索引建好；
  不预热的话，用户「改完角色属性再点商店/地图」就会在主线程冷建而卡一下（实测 1.3s）。新增写路径请确认有调 `_mark_dirty`。

### 8.4 已知硬成本与后续可做项（改动前先看这里）

- **单次写回 ≥0.2s**：`_apply_subs` 每次都要重拼整份文本（8.6MB 档纯字符串拼接就 ~160ms，是 Python str 的硬成本）。
  后续若要做「连续编辑合并写回」（多个字段的 sub 累积后一次性 `_apply_subs`），必须同时解决：延迟期间的 `self._text` 是旧值、
  其它入口（保存/复制/刷新列表/切换页签）要先 flush —— 风险较高，做之前先补测试。
- **道具表重建 / 角色页构建 / 排序**在主线程且要 ~1s 级：想再快只能改「惰性构建页签」（切换到时才建），但会改变
  「打开后 `tabs.count()` / 各页控件已就绪」的现有语义，GUI 测试大面积依赖，改动需同步改测试。
- **打开大档的 `char_model` 2.9s**：已用配对表把 6.9s 降到 2.9s；再快需要减少每角色重复扫描（可考虑缓存 `_entry_values` 单槽结果）。
- **「改一个值就把整页/整档重建」是最容易踩的坑（v2.17.0）**：队友入队/离队只改「队友对象在哪个容器」，
  页内其它数据完全没变 —— 若重建全部角色页要 **3.8s**（实测）。正确做法是**就地刷新**：
  把页内 `scope` 列表**原地改容器名**（页内所有回调引用同一个 list 对象）+ 用 `_rekey_char_scope(okey, nkey)` 重登记
  `_char_spin_map`/`_kangfu_ui`/`_char_open_cache` + 刷页签/页头/状态控件。
  **新增“搬动某个已建页/改某个登记键”的功能时，先看 `_party_after_move` 与 `_friend_pages` 登记表（含 `page` 控件引用），
  别直接调 `_apply_char_model`（3.8s）或 `_refresh_char_tabs`（≈ `char_model` + 建页）。**
  反查页签一律用 `self.tabs.indexOf(控件)`，**不要用页签文字匹配**（实测存档里 `langying`/`langying2` 中文名都叫「狼萤」）。

### 8.5 新增耗时功能的检查清单（提交前逐条过）

1. 用 `_scaffold/bench_ui_ops.py`（或 `bench_bulk_add.py`）量一下**主线程**耗时；>100ms 就继续走下面。
2. 能不能纯函数化？能 → 参数传 `text`、返回新 `text`/结果，然后 `_run_bg` 包起来（参考 `kangfu_add`/`equip_skill_model`）。
3. 必须在主线程建控件？→ 分块 + `_pump(进度文案)` + 重入守卫。
4. 是列表/表格批量操作？→ `addItems` / `_append_rows_local` / `_select_enabled_items`（勿逐行）。
5. 是循环里反复扫描同一个容器？→ 先收集子串区间再一次 `_apply_subs`（勿 O(k²)），或走配对表 O(1) 定位。
   同时**估算替换文本长度**：`_apply_subs` 的索引补丁按替换文本长度计费（MB 级 → 秒级），优先做最小跨度改写。
6. 改了 `self._text`？→ 确认调了 `_mark_dirty()`（触发索引异步预热），大档另可在 worker 里显式 `_get_struct_index(nt)` 预热。
7. **改的是某个「已建好的页/表格」背后的数据归属吗？** → 优先「就地改 scope/重登记键 + 只刷该页的控件」，
   不要整页/整档重建（见 8.4 末条）；登记表要成对维护（建页时登记、搬动时 `_rekey_*`、重建时清空重填）。
7. 忙时调用 `_run_bg` 会返回 `(False, "程序正忙")` → 记得同步回退或排队，别把用户的编辑丢掉。
8. 跑全套：核心 / GUI / `e2e_kangfu.py` / `e2e_chong_equip.py`（真实档增删往返必须逐字节一致），并同步更新本章基准表。
